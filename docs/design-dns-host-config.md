# Design: `dns-host-config`, a cross-platform DNS-routing crate

Status: proposal, not yet implemented. This is a design for a **new, separate**
crate (`dns-host-config`, Apache-2.0 — same license as `dns-stack`) that would
live alongside `dns-stack` in this repository and do the OS-side half of the
job described in [`setup.linux.md`](setup.linux.md) "Path B": push a resolver
address and a routing domain into the host's system DNS configuration, on
whichever DNS stack the host actually runs, and cleanly withdraw it again.
`dns-stack` itself stays out of this — see its README: "the crate never
touches ... an OS API." The two crates have **no dependency on each other**:
`dns-host-config` is useful with any DNS server, not just `dns-stack`'s.

## Terminology note

"Split DNS" is an overloaded term. This document — and the crate — is
**not** about split-horizon DNS (a server returning different answers
depending on the *source* of a query, see the Wikipedia article of that
name). Our resolver only ever sees queries from localhost via the OS's own
stub resolver, so no source-based logic is possible or needed. What we
actually mean, and what systemd-resolved's own docs call "split DNS", is
**conditional forwarding by queried name**: the OS resolver is told "queries
for suffix X go to resolver Y; everything else keeps using your normal
resolvers," decided purely by the name being looked up. This document uses
"conditional forwarding" or "routing-only domain" instead of "split DNS"
where precision matters.

## Why not RA/RDNSS, and why not depend on an existing crate

Recap of the reasoning that led here (see conversation history / commit log
for the fuller argument):

* RDNSS (RFC 8106) is advisory-only. Whether it results in a usable resolver
  depends on host OS, network manager, kernel sysctls, and consumer presence —
  none of which the sender can observe or control. Failure is silent.
* A single small crate, [`setdns`](https://crates.io/crates/setdns) (MIT,
  ~1900 LoC, published 2026-06, 67 downloads, one maintainer), already covers
  a similar surface (systemd-resolved, `/etc/resolver`, Windows NRPT) but is
  too new/unproven to depend on for something that needs root and touches
  system-wide network config.
* The most mature real-world prior art is Mullvad VPN's `talpid-dns` crate
  (part of the GPL-3.0-licensed `mullvadvpn-app` monorepo,
  <https://github.com/mullvad/mullvadvpn-app>, path `talpid-dns/`). It has
  been in production for years across Linux/macOS/Windows/Android. **Because
  it is GPL-3.0 and this project is Apache-2.0, no code from it may be
  copied.** Everything below is an architecture/API description written from
  reading it, not a derivative of its source.

## What `talpid-dns` actually does (architecture notes)

### Linux: a priority chain of four backends, runtime-selected

`talpid-dns/src/linux/mod.rs` tries, in order: **systemd-resolved →
NetworkManager → resolvconf → static `/etc/resolv.conf` edit**. Selection is
overridable via an env var (`TALPID_DNS_MODULE`) for testing. Each backend's
constructor doubles as a capability probe — if it fails, the chain falls
through to the next one. Key point: **detection is verification, not just
presence-checking**:

* *systemd-resolved*: it's not enough that the D-Bus name
  `org.freedesktop.resolve1` exists — `/etc/resolv.conf` must actually be a
  symlink to resolved's stub file (`/run/systemd/resolve/stub-resolv.conf` or
  the static-stub variant that points at loopback). If some other tool
  rewrites `/etc/resolv.conf` afterwards, `Link.SetDNS()` calls succeed but
  are silently ignored by the rest of the system — so the probe fails closed
  instead of reporting false success.
* *NetworkManager*: must confirm `DnsManager.RcManager != "unmanaged"`, must
  not be `dnsmasq` mode (NM can't manage per-interface DNS through dnsmasq),
  and its version must fall inside a hardcoded supported range
  (`1.16 ≤ version ≤ 1.26` in the version reviewed). Versions newer than that
  are treated as a hard error requiring fallback — a direct, coded response to
  real breakage (upstream NM changed DNS-reapply semantics across versions;
  see mullvadvpn-app issues #7451/#7452/#5500/#2468/#495 for the incident
  history that produced this range check).
* *resolvconf*: must not itself be a symlink to `resolvectl` (i.e. not
  actually systemd-resolved in disguise), and `/etc/resolv.conf` must show
  either the correct symlink target or a "Generated by resolvconf" marker.
  Also checks for a running `dnsmasq` with `no-resolv` set, which would ignore
  resolvconf's injected records entirely.
* *static `/etc/resolv.conf`*: last resort, global-only (no conditional
  forwarding, no interface scoping) — see crash-safety note below.

Wire-level details:
* **systemd-resolved**: D-Bus `org.freedesktop.resolve1.Manager.GetLink(ifindex)`
  → object path → `org.freedesktop.resolve1.Link.SetDNS(a(iay))`,
  `SetDomains(a(sb))`, optionally `SetDNSOverTLS("no")`. Reset via
  `SetDomains([])` + `SetDNS([])` (there is also a `Revert()` method that
  resets everything atomically; the higher-level code in the reviewed version
  uses the explicit-empty form instead). `talpid-dns` sets domains to
  `[(".", true)]`, i.e. "route *all* traffic through this resolver" — a
  full-override default route, not a routing-only domain. Our shape is the
  same API, just a different argument: `[("myvpn.example", true)]`, a real
  routing-only domain — this is the conditional-forwarding shape we actually
  want for `dns-stack`'s use case.
* **NetworkManager**: `Device.GetAppliedConnection()` → mutate the settings
  map (`ipv4`/`ipv6`: `method=manual`, `dns=[...]`, `dns-search=["~."]`,
  `dns-priority=-2147483647` to force it first) **while preserving existing
  routes** read from `IP4Config`/`IP6Config` (routes set out-of-band, e.g. by
  a route manager, must be copied back in or `Device.Reapply()` will drop
  them) → `Device.Reapply(settings, version_id, 0)`. Reset re-applies a
  backed-up copy of the original settings map, but only if the device is
  still in a "ready" state (`ACTIVATED`/`SECONDARY`/`IP_CHECK`) — otherwise
  it's a no-op, since a dead/removed device doesn't need resetting.
* **resolvconf**: shells out to the `resolvconf` binary (`-a <name>` with
  `nameserver ...` lines on stdin to add, `-d <name> -f` to delete), one
  record per interface.
* **static `/etc/resolv.conf`**: direct read/parse/write via the `resolv-conf`
  crate, guarded by a `parking_lot::Mutex`.

### The "reassert" pattern (static `/etc/resolv.conf` on Linux, all of macOS)

Two of the backends don't just set-and-forget; they **watch and reassert**:

* Linux static-file backend: an `inotify` watch on `/etc/resolv.conf`
  (`CLOSE_WRITE | DELETE_SELF | MOVE_SELF`). On any change, if the file no
  longer matches the desired nameservers, it's rewritten back — but the
  *previous* (foreign) content is captured as the new backup first, so a
  legitimate later change by the user/OS doesn't get silently reverted at
  `reset()` time.
* macOS: there is no per-interface DNS API usable from a `utun` device, so
  `talpid-dns` sets DNS on **every** network service via `SCDynamicStore`
  (keys matching `State:/Network/Service/.*/DNS` and
  `Setup:/Network/Service/.*/DNS`), then runs a background thread with its own
  CoreFoundation run loop that watches those same keys and re-applies the
  desired addresses whenever something (the OS, DHCP, the user) changes them.
  Changes are debounced (~0.5s, up to 5s under sustained churn) to avoid
  fighting a burst of legitimate churn. `reset()` restores the last-known
  per-service backup, or removes the key entirely if there was none. This is
  a **full-override, all-services** mechanism, not conditional forwarding —
  macOS's own native conditional-forwarding primitive, `/etc/resolver/<suffix>`
  files, is not used by this code path at all (that's a distinct mechanism
  worth offering as an alternative macOS backend for a routing-only use case
  like ours, where overriding *every* service's resolver is neither necessary
  nor desired).

Crash-safety differs by backend, and this is by design, not oversight:
* File-based backends persist a backup to disk
  (`/etc/resolv.conf.mullvadbackup`, or macOS's SCDynamicStore snapshot kept
  in-process) and **restore it on next startup** if a stale one is found —
  because a crashed process leaves the *file* mutated with no OS-level
  awareness that it's "temporary".
* API/D-Bus-scoped backends (systemd-resolved's per-link config, NetworkManager's
  per-device config, Windows' per-interface config) don't need this: the
  configuration is inherently scoped to an interface, so when the tunnel
  interface is destroyed, the OS discards the association on its own.
  `reset_before_interface_removal()` is a no-op for these but load-bearing for
  file-based ones.

### Windows

No NRPT in the reviewed code path. Primary mechanism is
`SetInterfaceDnsSettings` (`netioapi.h`, via the `windows-sys` crate), keyed by
interface **GUID** (derived from the interface's **LUID**, itself looked up
from the interface alias/name) — one call per address family (v4/v6), then
`DnsFlushResolverCache`. If that fails with `RPC_S_SERVER_UNAVAILABLE`
(the `dnscache` service isn't running — happens on some stripped-down/server
SKUs), it falls back to writing the nameserver list directly into the
registry under
`SYSTEM\CurrentControlSet\Services\Tcpip[6]\Parameters\Interfaces\<guid>`,
wrapped in a registry `Transaction` for atomicity, and skips the cache flush
(nothing to flush if the cache service is down). Both paths also try to
disable LLMNR/multicast (`EnableMulticast=0`) on the tunnel interface.
Reset is symmetric: same calls with an empty server list.

NRPT (`Add-DnsClientNrptRule` / the equivalent registry keys under
`SYSTEM\...\DNSClient\DnsPolicyConfig`) remains the right primitive if what's
wanted is conditional forwarding by suffix on Windows rather than a full
interface override — again, not something the reviewed code needs for its own
use case (full-override VPN privacy), but directly relevant to ours.

### Cross-cutting shape worth keeping

* One trait, one method set, one `#[cfg(target_os = ...)]`-selected `imp`
  module — exactly the same shape `dns-stack` already uses for transport.
* `set()` always tears down and rebuilds the backend from scratch rather than
  reusing a cached "detected backend" — the system's DNS management can
  change between calls (NetworkManager restarts, resolved gets installed,
  etc.), so trusting a stale detection result is itself a source of the
  "silently doesn't work" failure mode this whole design is trying to avoid.
* Every "is X available" check is also "is X *actually wired up*", per the
  systemd-resolved/NetworkManager examples above. Fail closed to the next
  backend in the chain, never succeed at a no-op.

## Proposed crate design for `dns-host-config`

### Public API

```rust
pub struct DnsRouteConfig {
    pub servers: Vec<IpAddr>,
    /// Empty = full override of the default resolver.
    /// Non-empty = routing-only domains: only names under these suffixes
    /// go to `servers`; everything else keeps using the host's existing
    /// resolver(s). This is the shape `dns-stack`'s use case needs.
    pub routing_domains: Vec<String>,
}

pub trait DnsRoute: Sized {
    type Error: std::error::Error + Send + Sync + 'static;

    fn new() -> Result<Self, Self::Error>;
    fn set(&mut self, interface: &str, config: &DnsRouteConfig) -> Result<(), Self::Error>;
    fn reset(&mut self) -> Result<(), Self::Error>;
    /// Default = reset(). Override only where the interface's own teardown
    /// isn't enough to also undo the DNS-side state (i.e. file-based
    /// backends).
    fn reset_before_interface_removal(&mut self) -> Result<(), Self::Error> {
        self.reset()
    }
}
```

A public `PlatformDnsRoute` type alias/wrapper picks the right `imp` module
per `target_os`, same pattern as `dns-stack`'s existing `In`/transport
generic.

### Module layout

```
src/
  lib.rs                 // trait, DnsRouteConfig, target_os dispatch
  linux/
    mod.rs               // priority chain + env override + auto-detect
    systemd_resolved.rs   // D-Bus (zbus), the resolv.conf-symlink probe
    network_manager.rs    // D-Bus (zbus or dbus-rs), version-range gate
    resolvconf.rs          // shells out, dnsmasq-misconfiguration probe
    static_resolv_conf.rs  // file + inotify reassert + crash-recovery backup
  macos.rs                 // SCDynamicStore, reassert thread; OR:
  macos/
    mod.rs
    dynamic_store.rs        // the talpid-style full-override backend
    resolver_files.rs        // /etc/resolver/<suffix>, routing-only backend
  windows/
    mod.rs                  // iphlpapi-first, tcpip-registry fallback
    iphlpapi.rs
    tcpip.rs
    nrpt.rs                  // optional: conditional-forwarding-by-suffix backend
```

Each backend gated behind its own Cargo feature, default-off except a
sensible per-platform default set, so consumers who only need e.g.
systemd-resolved don't pull in `dbus`/NetworkManager bindings.

### Linux backend selection

Same four-way chain as `talpid-dns`, with the same fail-closed verification
per backend (symlink check for resolved, version+RcManager check for NM,
binary-identity check for resolvconf). Env var override for tests, e.g.
`DNS_HOST_CONFIG_BACKEND=systemd|network-manager|resolvconf|static-file`.

### macOS: two backends, pick based on intent

* `resolver_files` (native `/etc/resolver/<suffix>`, one file per routing
  domain, up to 3 nameservers each): the right default for `dns-stack`'s
  actual use case (peer names under one suffix), since it's scoped by domain
  rather than clobbering every network service, and needs no background
  thread.
* `dynamic_store` (talpid-style, SCDynamicStore + reassert thread): only
  needed if a future consumer wants to override the whole system's DNS, not
  needed for the conditional-forwarding case.

### Windows: two backends, same split

* `iphlpapi`/`tcpip` (talpid-style interface override) for the full-override
  case.
* `nrpt` for conditional forwarding by suffix, matching `resolver_files` on
  macOS and the routing-domain form of `SetDomains` on Linux.

For `dns-stack`'s actual need (routing-only domain for VPN peer names), the
three "routing-only" backends — Linux systemd-resolved with a real routing
domain, macOS `/etc/resolver/<suffix>`, Windows NRPT — are the ones that
matter first; the full-override backends (NetworkManager full takeover,
macOS SCDynamicStore, Windows iphlpapi/tcpip) are lower priority and mostly
relevant if a future consumer wants full-override behavior instead.

### Suggested phasing

1. **Linux, systemd-resolved only** + the resolv.conf-symlink verification +
   static-`/etc/resolv.conf` fallback (with inotify reassert and
   crash-recovery backup). This alone delivers the "host you control" story
   from `setup.linux.md` Path B, is fully testable with the Docker/systemd
   harness this repo already has (`docker/run-discovery.sh`,
   `tests/discovery_linux.rs`), and is a shippable first crate version.
2. Linux NetworkManager + resolvconf backends — completes Linux
   auto-detection.
3. macOS `/etc/resolver/<suffix>` (routing-only) — small, no background
   thread, good second platform.
4. Windows NRPT (routing-only) — registry-only, no background thread.
5. Optional full-override backends (NetworkManager full takeover, macOS
   SCDynamicStore+reassert, Windows iphlpapi/tcpip) if a consumer ever needs
   full-override DNS instead of conditional forwarding.

### Testing strategy

Mirror this repo's existing pattern: unit-test the pure logic (settings
diffing/merging, backup-state bookkeeping, backend-selection priority)
without touching the OS, and keep OS-touching tests behind `#[ignore]` + a
privileged Docker container (as `tests/discovery_linux.rs` already does for
the RA/RDNSS path) — e.g. a systemd container to exercise the real
systemd-resolved backend end-to-end, verifying `resolvectl
domain`/`resolvectl dns` reflect what was set, and that `reset()` cleans it
back up.
